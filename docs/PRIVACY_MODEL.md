# ShieldScore — Zero-Knowledge Privacy Architecture & Cryptographic Invariants

This technical dossier details the cryptographic underpinnings, threat model, and zero-knowledge privacy boundaries implemented in **ShieldScore** on the Midnight Network.

---

## 1. Threat Model & Security Objectives

In conventional credit scoring and lending architectures, the lender acts as an adversarial data collector from the borrower's perspective. Once financial documents are transmitted:
- They can be subpoenaed, leaked, or ransomed in data breaches.
- Secondary profiling (predatory loan terms, insurance discrimination) becomes possible.
- The borrower loses all sovereignty over their private financial life.

### Primary Security Objectives of ShieldScore:
1. **Confidentiality:** The verifier and any blockchain observer must learn *zero* information regarding the borrower's exact credit score, salary, debt obligations, or collateral balances beyond the binary claim: *“Borrower satisfies Policy P”*.
2. **Soundness:** A borrower whose credit profile does not meet Policy $P$ must be mathematically unable to convince the on-chain circuit verifier, except with negligible probability $\epsilon \approx 2^{-128}$.
3. **Completeness:** An honest borrower whose financial metrics satisfy Policy $P$ must always be able to produce a valid proof $\pi$ that verifies on-chain.
4. **Identity Non-Replayability:** Zero-knowledge proofs generated by Borrower $A$ cannot be stolen or replayed by Borrower $B$ to claim false eligibility.

## 2. Dual-State Execution & The Selective Disclosure Barrier

Midnight splits computation across two disjoint domains:

```
+-----------------------------------------------------------------------+
| CLIENT-SIDE PRIVATE DOMAIN (Off-Chain Execution Memory)                |
|                                                                       |
|  [ Private Financial Witness ]                                        |
|  - creditScore: 780                                                   |
|  - annualIncome: $120,000                                             |
|  - debtToIncomeBps: 2800 (28.00%)                                     |
|  - collateralRatioBps: 21000 (210.00%)                                |
|  - applicantSalt: 0x9f4a...                                           |
|                                                                       |
|        │                                                              |
|        ▼                                                              |
|  [ Compact Circuit Constraints ]                                      |
|  - assert(score >= minScore)                                          |
|  - assert(income >= minIncome)                                        |
|  - assert(dti <= maxDTI)                                              |
|  - assert(collateral >= minCollateral)                                |
|  - saltCommitment = persistentHash(applicantSalt)                     |
|                                                                       |
|        │                                                              |
|        ▼                                                              |
|  [ Local Prover (WASM / Docker:6300) ] ──> Generates ZK-SNARK Proof π |
+-----------------------------------------------------------------------+
                                   │
               Explicit Boundary: disclose(true, tier, commitment)
                                   │
                                   ▼
+-----------------------------------------------------------------------+
| MIDNIGHT PUBLIC CONSENSUS DOMAIN (On-Chain Public Ledger)             |
|                                                                       |
|  [ Verifier Smart Contract ]                                          |
|  - Verifies proof π using verifying key vk                            |
|  - Updates public ledger:                                             |
|      * lastVerificationResult = true                                  |
|      * lastVerifiedRiskTier = 1 (Tier A Prime)                        |
|      * commitment = 0x9f4a...                                         |
|      * timestamp = 1788800000                                         |
+-----------------------------------------------------------------------+
```

### The `disclose()` Compiler Invariant
In Compact, data origin tracking is enforced at compile time. Any value derived from a `witness` function is tainted as private. The compiler prevents private values from:
- Being assigned to any `ledger` variable.
- Being returned from any `export circuit`.
- Being passed to foreign contracts.

Attempting to assign a private witness value directly to the public ledger without `disclose(...)` causes an immediate compilation failure:
```
error: value derived from witness cannot cross privacy boundary without disclose()
```

## 3. Cryptographic Primitives

### Pedersen & Poseidon Commitments
To bind the applicant's identity without leaking identity identifiers, ShieldScore computes:
$$\text{Commitment} = \text{persistentHash}(\text{applicantSalt})$$
The commitment is collision-resistant and hiding, ensuring:
1. Two different users with identical credit scores have completely distinct on-chain commitments.
2. The user can later prove ownership of the commitment by proving knowledge of `applicantSalt`.

### Succinct Non-Interactive Zero-Knowledge Arguments of Knowledge (zk-SNARKs)
Proofs are generated over algebraic constraint systems (R1CS/Plonk). Proving complexity is $O(C \log C)$ on the client, while on-chain verification is $O(1)$, executing in milliseconds with constant-size calldata.
